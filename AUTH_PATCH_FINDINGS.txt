2. THE LOCAL TOKEN VALIDATION FUNCTION (best candidate)
-------------------------------------------------------
Function 0x10008ef58 .. 0x10008f174 (540 bytes) returns a Bool in w0.

  0x10008ef58  pacibsp
  0x10008ef5c  ... frame setup ...
  0x10008ef78  cbz  x19, 0x10008f094        ; nil token -> false
  0x10008ef80  bl   0x10024e240             ; isEmpty?
  0x10008ef84  cbz  w0,  0x10008f094        ; empty -> false
  0x10008ef88  bl   0x10024d480
  0x10008ef90  cbnz x0,  0x10008f094        ; extra guard -> false
  ...
  0x10008f018  bl   0x100097304             ; build/compare helper
  0x10008f078  bl   0x100097410             ; payload/signature check
  0x10008f088  tbz  w23, #0, 0x10008f0c0   ; <-- DECISION
  0x10008f08c  mov  w21, #1
  0x10008f090  b    0x10008f0f8             ; return true
  0x10008f0c0  ... sets status 6, message "Missing or invalid auth token."
  0x10008f0f4  mov  w21, #0                  ; return false

Callers: 0x1000949c4 and 0x1000952b0 (both inside the TrollGame
validation flow region 0x100094xxx-0x100095xxx).

Helper 0x100097304 .. 0x100097410 calls 0x10008f174 first and returns nil
when that fails (tbz w0,#0 -> x22=0), otherwise builds a string and checks
it. Helper 0x100097410 .. 0x10009798c parses keys out of a dictionary
(subscript at 0x100249500) and compares them.

IMPORTANT CAVEAT: this function is in the same region as the licence flow
that patch_gate.py already neutralises, and I could not prove by xref that it
is the *aov.anhvu.cc* config-sync comparison rather than the TrollGame token
check. The "aov_remote_cosmetic_config_v1" / "https://aov.anhvu.cc/api/config"
pair is referenced from Swift literals in __const, and no direct adrp+add
reference to either cstring exists in __text, so the sync function has to be
located through the Swift literal struct, not by a cstring xref.


3. PATCHES THAT WOULD MAKE THE GATE ALWAYS TRUSTED
--------------------------------------------------
Option A (narrowest, one branch; recommended first try)

  0x10008f088   tbz w23, #0, 0x10008f0c0
  -> nop                                    bytes: 1f 20 03 d5

  Effect: the local validation result is ignored, flow falls through to
  "mov w21,#1" and returns true. The nil/empty guards above still run, so a
  completely absent token still fails. If the flicker is a *mismatch* rather
  than a missing token, this is the correct minimal fix.

Option B (whole function; mirrors the existing patch_gate.py style)

  0x10008ef58   pacibsp
  -> mov w0, #1 ; ret                       bytes: 20 00 80 52 c0 03 5f d6

  Effect: the validator returns true unconditionally, including for a nil
  token. Use if the dev build must never block on auth at all.

Both are in __text and both fit inside existing instruction slots, so no
layout changes are needed. CodeDirectory page hashes must be recomputed
afterwards: reuse tools/patch_gate.py:resign() unchanged.

Suggested implementation: add a second PATCHES entry to tools/patch_gate.py,
e.g.

  (0x10008F088, NOP, "authTokenSig validation -> always trusted")

or a new tools/patch_auth.py that imports resign() from patch_gate and applies
Option A, so the two patches stay separable and revertible.

Then:
  export PYTHONPATH=$PWD/pylibs
  python3 tools/patch_gate.py work/Payload/DSGames.app/DSGames \
      work/patched/Payload/DSGames.app/DSGames
  python3 tools/patch_auth.py   work/patched/Payload/DSGames.app/DSGames \
      work/patched/Payload/DSGames.app/DSGames
  python3 tools/pack_ipa.py work/patched/Payload/DSGames.app \
      deadshot_dev_build_unlocked.ipa


4. OPEN ITEMS (what still needs confirming)
-------------------------------------------
a) Confirm which function actually performs the aov.anhvu.cc config sync.
   Method: find the __const literal struct holding 0x10025ed10
   ("https://aov.anhvu.cc/api/config"), then find the adrp+add that
   materialises *that struct address* (the cstring itself is only reached
   through the struct). Current sweeps hit 0 because they targeted the
   cstring VA directly.
b) Once found, check whether its comparison is a string compare
   (memcmp/==) against the keychain authTokenSig or a signature check
   (SecKeyVerifySignature / P256). Patch the branch, not the crypto, unless
   the crypto is what is failing.
c) The .dsi-m1 file holds a sha256 that matches neither the original nor
   the patched binary, so it is not a live integrity check; leave it alone
   (already documented in AGENTS.md).
d) Nothing here has been verified on a device. Page hashes verify in the
   file, but only a launch on-device proves the gate is gone.
